## Рішення і зміни — два логи й місток між ними (D-19)

**Рішення живе в `docs/DECISIONS.md`. Зміна живе в історії Git. Зв'язує їх рядок
`Decision: D-NN` у повідомленні коміту.**

Навіщо два логи, а не один: реєстр відповідає на питання «що діє **зараз** і чому»,
історія Git — «що і **коли** змінилось». Це різні питання, і зводити їх в один документ
означає або переписувати минуле, або втратити актуальний стан.

### Хто пише і в який момент

- **Ухвалює рішення Андрій. Формулює рядок Клод. Підтверджує Андрій.**
- Момент запису — **ухвалення**, а не реалізація. Рішення «не робимо Х» повноцінне
  й коду не має ніколи (приклад — D-12).
- **Само не створюється.** З готового коду видно результат, але не видно, які варіанти
  відкинули — а рішення це саме вибір. Автоматизувати можна лише перевірку наявності
  мітки, не її зміст.

### Що записувати як рішення

Фільтр — одне питання: **чи були реальні альтернативи і чи спитають через півроку
«а чому саме так?»**

- Так → рядок у `DECISIONS.md`, номер D-NN.
- Ні, це просто спосіб виконати вже ухвалене → це робота, не рішення. Номер не потрібен.

Якщо номер заводити на кожен рух, реєстр за місяць стане нечитабельним — і механізм
помре не від складності, а від шуму.

### Мітка в коміті

Коміт, що виконує рішення, містить мітку **в самому останньому блоці** повідомлення,
без порожнього рядка перед сусідніми мітками:

```
docs: короткий опис зміни

Тіло: що зробили і чому.

Decision: D-19
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

**Порожній рядок перед `Decision:` ламає механізм.** Git вважає блоком трейлерів лише
останній абзац; відділена мітка стає звичайним текстом, і `%(trailers:key=Decision)`
поверне порожнечу. Перевірено 2026-08-13 на коміті `6ecdcc8` — довелось виправляти
через `--amend`.

- Мітка **не диктує розмір коміту**: одне рішення може мати один коміт, десять або жоден.
  Розмір коміту визначає зручність відкату, а не реєстр.
- Коміт може нести кілька міток — по рядку на кожну, всі в тому ж блоці.
- Рутинна зміна без рішення (правопис, форматування, дрібне прибирання) позначається
  `Decision: none` — це **свідома відповідь** «тут рішення немає», а не забудькуватість.

### Перевірка при коміті (D-20)

Хук `.githooks/commit-msg` не пропускає коміт, у якого:

- немає мітки взагалі;
- мітка відділена порожнім рядком (Git її не бачить — пастка з `6ecdcc8`);
- номер не існує в `docs/DECISIONS.md` — тобто **реєстр веде, коміт наздоганяє**.

Хук друкує повну інструкцію просто в тексті помилки — шукати правило не доведеться.
Там же він підказує **наступний вільний номер** рішення, щоб не промахнутись.
Обхід разово: `git commit --no-verify`.

**На кожній машині один раз:** `git config core.hooksPath .githooks`
(деталі — [`.githooks/README.md`](.githooks/README.md)).

### Як читати

| Питання | Команда / місце |
|---|---|
| Що діє зараз і чому | `docs/DECISIONS.md` |
| Що змінилось на цьому рівні | `git log --oneline -- <шлях до папки чи файлу>` |
| Які зміни породило рішення D-NN | `git log --oneline -E --grep="Decision: D-NN$"` |
| Яке рішення стоїть за цими змінами | `git log --format="%h %s -> %(trailers:key=Decision,valueonly)" -- <шлях>` |

**Знак `$` у пошуку обов'язковий** — це «кінець рядка». Без нього запит по `D-1`
знайде ще й `D-19`, `D-14`, `D-16`: коротший номер є підрядком довшого.

Рівень задається **шляхом**, а не окремим файлом. Тому окремих `CHANGELOG.md` по папках
ми не заводимо: їх треба дописувати руками, одного разу забув — і файл каже неправду.
Якщо колись знадобиться людський changelog для релізу — його **генерують** з історії.

### Виняток — зміни поза Git

Версія плагіна, оновлення Claude Code, налаштування зовнішнього сервісу комітом не є,
тож Git їх не побачить. Такі зміни записуються рядком у розділ
«Зміни середовища» в `DECISIONS.md` — руками, з датою.

## Робота з двох комп'ютерів
- Розгортання нової машини: `docs/SETUP-NEW-MACHINE.md`
- Проєкт синхронізується через Git: `git pull` перед роботою, `git push` після.
- Шлях до папки на кожному ПК свій (профілі Windows різні) — не покладатися на
  абсолютні шляхи, тільки на відносні від кореня репозиторію.
- Локальні проєкти Cowork між ПК не синхронізуються (обмеження платформи) —
  на кожному комп'ютері створюється свій, наведений на локальний клон репозиторію.
  Спільним є вміст папки, а не проєкт.
