# .githooks — перевірки, що спрацьовують під час коміту

## Що тут лежить

| Файл | Коли спрацьовує | Що робить |
|---|---|---|
| `commit-msg` | під час кожного `git commit` | не пропускає коміт без мітки `Decision:` |
| `post-merge` | після `git pull` | друкує підказку запустити `/session-brief` — нічого не блокує |
| `pre-push` | перед `git push` | друкує нагадування запустити `/pm-end` — нічого не блокує |

`post-merge` і `pre-push` — обидва чисте нагадування, завжди завершуються успішно. (У Git немає хука "після push" — `pre-push` спрацьовує до відправки, це найближчий робочий еквівалент.)

> **Історія.** До 2026-08-16 `pre-push` намагався спитати `[y/N]` в терміналі (через `/dev/tty`) і на "так" зупинити push. Дві спроби (коміти `25eb4e8`, `ce52b01`) не змогли зробити це надійним: з PowerShell у VS Code (ConPTY) читання з `/dev/tty` не блокувало — push проходив без питання, ніби відповіли "ні". Спрощено до чистого нагадування — узгоджується з правилом D-21 («git hooks лише нагадують»).

## Чому папка тут, а не в `.git/hooks/`

Стандартна папка `.git/hooks/` лежить **поза репозиторієм** і через `git push`/`git pull` не передається. На другому комп'ютері хука просто не було б — і ти б цього не помітив.

Тому файли лежать тут (звичайна тека проєкту, потрапляє в git), а Git отримує на них вказівник однією командою. **На кожній машині її треба виконати один раз:**

```bash
git config core.hooksPath .githooks
```

Перевірити, що ввімкнено:

```bash
git config core.hooksPath
```

Має вивести `.githooks`. Якщо порожньо — хуки не працюють, виконай команду вище.

## Де правило, а не його копія

Що саме писати в мітці, які є варіанти й навіщо це все — **[`CLAUDE.md` § Рішення і зміни](../CLAUDE.md)**. Тут цього тексту навмисно немає: скопіювати правило означало б завести другу копію, яка з часом розійдеться з першою (див. «правило єдиного джерела»).

Найчастіше правило й шукати не доведеться — хук друкує повну інструкцію просто в тексті помилки, у ту саму секунду, коли вона потрібна.

## Якщо треба обійти

```bash
git commit --no-verify
```

Це поручні від забудькуватості, а не замок. Але якщо тягнешся до `--no-verify` частіше ніж раз на місяць — проблема не в хуку, а в правилі; тоді його треба переглядати.
