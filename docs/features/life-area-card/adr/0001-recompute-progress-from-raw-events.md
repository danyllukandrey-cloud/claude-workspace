# 0001 — Recompute progress from raw events, never store a derived percentage

- **Status:** Accepted
- **Date:** 2026-08-23
- **Deciders:** Андрій Данилюк (з Клодом під час Socratic-проходу `design`)

## Context

Картка показує частку виконання цілі (spec.md AC-09, AC-09b, AC-05) і, за новим рішенням цієї сесії ([D-57](../../../DECISIONS.md#d-57)), історію останніх записів (US-12). Обидві спираються на одні й ті самі дані — записи подій метрик-блоку. Design-review (Engineer, блок 8) раніше поставив питання «чи фіксуємо правило: похідні числа не зберігаємо, лише перераховуємо з сирих подій» як нерозкрите (spec.md §8).

## Decision drivers

- Історія записів (US-12, AC-12, AC-13) вимагає зберігати самі події — без них нема що показувати в списку останніх N записів.
- Виправлення чи відкат запису (AC-12) не повинні лишати застарілий кешований відсоток — якщо прогрес кешується окремо, кожна правка вимагає синхронного перерахунку в двох місцях (ризик розходження).
- Модель цілі з spec.md AC-05/AC-05b («постійний процес» без знаменника, ціль перевищена — capped) — обчислення нетривіальне і має існувати в одному місці, не дублюватись між кешем і перерахунком.

## Considered options

1. **Зберігати сирі події, рахувати прогрес щоразу під час читання** — жодного кешованого числа в сховищі.
2. **Зберігати готовий відсоток, оновлювати при кожному записі** — швидше читання, але два джерела правди (сирі події + кешоване число).

## Decision outcome

**Chosen:** Option 1. Історія записів (US-12) і так вимагає зберігати сирі події — тож кешоване число було б чистим дублюванням, яке треба тримати синхронним при кожній правці/відкоті (AC-12). Одне джерело правди усуває цілий клас багів «показане число розійшлося з реальними записами».

## Consequences

**Positive**
- Виправлення чи відкат запису (AC-12) автоматично дає правильний прогрес — перераховувати нема що окремо.
- Модель "постійний процес"/"ціль перевищена" (AC-05/AC-05b) рахується в одному місці.

**Negative**
- Читання картки трохи дорожче (сума/агрегація на льоту), а не пряме читання одного поля. При обсягах цієї фічі (десятки записів на картку, MVP) — не проблема.

**Neutral**
- При зростанні кількості записів на картку до тисяч (малоймовірно для MVP) перерахунок на льоту може знадобитись оптимізувати (кешування з інвалідацією) — не зараз, зафіксовано як прийнятний борг у sad.md §11.
