# 0006 — Use a domain sentinel result for expected errors, never throw

- **Status:** Accepted
- **Date:** 2026-08-26
- **Deciders:** Андрій + Клод під час `/sdd:design agent`

## Context

`agent` — перша фіча, чий код реально живе на бекенді ([ADR-0005](0005-layered-domain-app-infra-ports-backend.md)); шарова структура `domain/app/infra/ports` уже вирішена, але жоден шар ще не визначив, **як** повідомляти про очікувану помилку (Claude недоступний, правило порушено, пропозиція не пройшла guard-перевірку) вгору по шарах. Рішення тут неминуче стає конвенцією для будь-якої майбутньої backend-фічі, не лише для `agent` — так само, як ADR-0005.

## Decision drivers

- spec §8 OQ і §6 Runtime view (Critical flow 2) уже описують «Claude недоступний, без retry, текст користувача не втрачено» — це очікуваний, не аварійний, шлях, отже повинен мати явний тип, а не покладатись на try/catch навколо мережевого виклику.
- ADR-0004 (prompt + post-hoc guard): результат guard-перевірки («правило порушено») — це рішення бізнес-логіки domain-шару, яке app і ports мають вміти відрізнити від збою інфраструктури.
- domain-шар (ADR-0005) не має зовнішніх залежностей і тестується без мережі/бази — винятки, що перетинають межі шарів, ускладнюють саме це тестування (стек викликів, приховані side-exit).
- Одна людина в темпі ~1-2 год/тиждень (§2 Constraints) — конвенція, обрана зараз, буде відтворюватись копіюванням у кожній наступній backend-фічі, тож вартість помилки тут висока.

## Considered options

1. **Sentinel-результат (типізований union: `Ok<T> | Err<E>`)** — domain-функції повертають значення, ніколи не кидають виняток для очікуваного збою; `app`-шар мапить `Err` у ports-помилку; `ports`/HTTP-шар мапить її в JSON `{code, message}`.
2. **Виключення (exceptions) наскрізь усіх шарів** — domain кидає typed error class, app/ports ловлять через try/catch і мапують у HTTP-відповідь.

## Decision outcome

**Чат-вибір: Option 1.** Явний тип результату робить очікувану помилку частиною сигнатури функції — виклик `handle-message.ts` не може «забути» обробити «Claude недоступний» так, як можна забути `catch`. Це узгоджується з причиною ADR-0005 (domain тестується ізольовано): unit-тест guard-перевірки перевіряє повернене значення, не ловить виняток. Ціна (трохи більше boilerplate на кожен виклик) прийнятна для темпу проєкту — конвенція пишеться раз, копіюється в кожну наступну фічу.

## Consequences

**Positive**
- Кожна точка виклику явно бачить у сигнатурі, що результат може бути помилкою — неможливо «забути» обробити її мовчки.
- domain-шар лишається тестованим без мережі й без бази (той самий аргумент, що й ADR-0005): unit-тест звіряє значення `Err`, не ставить `expect().toThrow()`.
- Одна конвенція на весь бекенд — наступна фіча (синхронізація, OAuth конекторів) не вигадує власний стиль обробки помилок.

**Negative**
- Більше коду на кожен виклик (перевірка `if (result.ok)` замість голого виклику) — накладні витрати відчутні на маленьких функціях.
- Потребує дисципліни: спокуса кинути звичайний `throw` для «швидкого» випадку завжди є, особливо в `infra/` при роботі з бібліотеками, що самі кидають виключення (тоді `infra/`-обгортка ловить їх і конвертує в sentinel на межі з domain/app).

**Neutral**
- Аварійні (непередбачені) збої — баг у коді, обрив з'єднання з базою на рівні драйвера — і далі йдуть через звичайний виняток і глобальний error-handler на межі HTTP; sentinel стосується лише **очікуваних** доменних результатів.
