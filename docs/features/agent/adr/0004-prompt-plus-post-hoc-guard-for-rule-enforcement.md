# 0004 — Enforce user imperative rules via system prompt plus a post-hoc guard check

- **Status:** Accepted
- **Date:** 2026-08-25
- **Deciders:** Андрій + Клод під час `/sdd:design agent`

## Context

`spec.md` §1 називає це найгострішим ризиком фічі (`devils-advocate`, 2026-08-25): механізм примусу власного імперативного правила користувача (AC-07, D-35) не був спроєктований — тихе порушення правила не виявлялось би й не логувалось. Spec §8 прямо відклав це рішення до `/sdd:design agent`. AC-07 вимагає, щоб відповідь агента слідувала правилу користувача, а не дефолтній поведінці мовної моделі.

## Decision drivers

- spec §1: найгостріший ризик фічі за незалежним ревʼю (`devils-advocate`).
- AC-07/AC-08/AC-12/AC-14 — правила (глобальні + перевизначення картки) мають діяти на **кожній** відповіді агента, не як побажання.
- spec §6: «Точність дотримання власного правила — TBD, залежить від невирішеного механізму примусу» — це рішення прямо визначає, чим цю метрику можна буде виміряти.
- Latency-цілі (§6 NFR, ≤4000мс) обмежують, скільки додаткових LLM-викликів можна собі дозволити на шляху пропозиції.

## Considered options

1. **Лише системний промпт** — правила передаються мовній моделі текстом у системному промпті; жодної окремої перевірки відповіді.
2. **Prompt + post-hoc guard-перевірка** — правила й у системному промпті, і backend після кожної відповіді агента прогонятиме її окремим легким перевірником-правилом (наприклад другий, дешевший LLM-виклик «чи порушено правило X?», або структурний regex/keyword-фільтр там, де правило це дозволяє) перед тим, як відповідь піде до користувача.
3. **Fine-tuning/жорстке кодування правил у коді** — розглядалось і відкинуто: куратоване меню категорій (D-27) і власний вільний текст (D-35) не мапляться на кінцевий набір правил, який можна закодувати статично; кожен користувач формулює своє.

## Decision outcome

**Chosen:** Option 2. Варіант 1 залишає рівно той ризик, який `devils-advocate` і `spec.md` §1 явно назвали найгострішим — «сподівання», без виявлення чи логування порушення. Варіант 3 не масштабується на довільний текст власного правила (D-35). Варіант 2 додає перевірний шар без переписування архітектури: правило й далі формулюється природною мовою (сумісно з D-27/D-35), але backend отримує точку, де порушення **видно** — це основа і для метрики «точність дотримання» (§6 NFR, зараз TBD), і для майбутнього логування порушень.

## Consequences

**Positive**
- Порушення правила стає **видимою** подією (можна залогувати, порахувати метрику §6, показати користувачу), а не мовчазним провалом.
- Точне число цільової точності (§6 NFR «TBD») тепер вимірюване — стає предметом `data-model`/`tasks`, не риторичним питанням.

**Negative**
- Додатковий крок на шляху пропозиції — ризик для latency-цілі (p95 ≤4000мс); конкретна реалізація guard-перевірки (окремий легкий LLM-виклик чи дешевший локальний фільтр) і бюджет часу на неї не визначені тут — залишається відкритим у §11.
- Додаткова вартість (ще один виклик LLM або обчислення) на кожну відповідь агента.

**Neutral**
- Guard-перевірка може почати як проста (keyword/regex для типових категорій меню, D-27) і рости до LLM-based лише там, де правило вільного тексту (D-35) складніше формалізувати — це деталь реалізації, не предмет цього ADR.

## Пізніша примітка (2026-08-28, D-82)

Зовнішнє дослідження курсу «Agentic Engineering» (модулі 2.6 Prompt Injection & Defenses, 7.4 Dynamic Workflows, 10.3 Evals & Regression) показало: цей ADR узгоджується з курсом у філософії («охоронець після факту»), але мілкіший за рекомендований defense-in-depth — курс радить дві незалежні перевірки (convergence checking) замість однієї повторної спроби, pre-execution фільтр дешевою моделлю перед основною відповіддю, і регулярну eval-інфраструктуру (Promptfoo-подібний сьют), щоб дійсно вимірювати ≥95% (§6 NFR), а не лише декларувати число. **Рішення (D-82):** свідомо приймаємо цей розрив для v1, підсилення — після v1, разом з рештою KPI-інфраструктури.

## Пізніша примітка (2026-08-30, D-94)

Цей ADR вирішує лише ПЕРЕВІРКУ відповіді агента — що робити ПІСЛЯ того, як модель уже щось згенерувала. Лишається окреме, раніше не назване питання: **як саме подавати «характер» (D-37) і «кордони» (AC-07/AC-08, D-35) моделі ДО генерації**, щоб вона рідше їх порушувала — тобто зменшити навантаження на сам guard-шар, а не лише ловити його провали.

Спостереження зі спорідненого прикладу — цей самий робочий простір, де `CLAUDE.md` організує роботу Клода над проєктом ПЛАН. Два принципи, які там реально працюють і мають пряму паралель для Агента:

1. **Правило подається заново, не «пригадується» з давнішньої точки розмови.** `CLAUDE.md` перечитується Клодом із нуля на старті кожної сесії — не лишається «десь на початку» довгого чату, де programmatically легше загубитись серед сотень наступних повідомлень. Пряма паралель для Агента: **системний промпт (характер + кордони) передається моделі повторно при КОЖНОМУ виклику**, не лише в першому повідомленні розмови користувача, яка може тривати тижнями.
2. **Вузький, контекстний набір інструкцій замість одного все-в-одному промпту.** Клод не тримає постійно в увазі деталі всіх ≈30 skills проєкту — конкретна процедура (`/pm-start`, `sdd:specify` тощо) підвантажується лише в момент, коли вона реально потрібна. Пряма паралель для Агента: замість одного гігантського системного промпту «на всі випадки життя» — вужчий, контекстний шматок інструкцій під конкретний тип взаємодії (запис у картку / рефлексивне запитання / огляд Структури тощо), що підвантажується під ситуацію.

**Рішення (D-94):** приймаємо цей напрямок як план на наступну версію (після v1) — разом із рештою defense-in-depth-інфраструктури з D-82, тим самим тригером повернення (Агент ще не збудований, нема на чому реалізовувати). Записується тут, а не новою секцією ADR, бо це те саме рішення «guard після факту», лише доповнене — не окрема архітектурна розвилка з власними альтернативами.
