# 0001 — Split agent across three target surfaces: backend-service, web-frontend, worker

- **Status:** Accepted
- **Date:** 2026-08-25
- **Deciders:** Андрій (архітектор/product owner) + Клод під час сократичного проходу `/sdd:design agent`

## Context

Фіча `agent` вводить три різні за природою обов'язки: (1) обробка чат-повідомлень/вкладень із підтвердженням запису, (2) вбудований UI чату в PWA, з яким користувач фактично спілкується, і (3) періодичні звіти активності (AC-11), що формуються за розкладом, а не у відповідь на запит користувача. `design` мусить явно вибрати, скільки й яких C4-контейнерів (target surfaces) ця фіча вводить — рішення гейтується bласт-радіус перевіркою і записується у frontmatter `target_surfaces`, звідки його читають усі наступні етапи (`api`/`sequences`/`tasks`/`plan-tests`).

## Decision drivers

- Latency-цілі spec §6 NFR (p95 ≤4000мс пропозиція, ≤1000мс підтвердження) стосуються синхронного шляху чату — генерація звіту раз на тиждень/місяць/квартал не повинна ділити ресурси чи блокувати цей шлях.
- AC-11 (звіт активності) прямо каже «настав час чергового автоматичного звіту» — це подієво-часовий тригер, не запит користувача; С4-таксономія (`_shared/surfaces.md`) визначає це як `worker` (event-consumer/scheduled job, без request/response поверхні).
- Продукт уже описаний і спроєктований під «вбудований чат» як основний канал (`Product_Vision.md §5`, `design-review.md` Блок 5-7) — це вимагає реального UI-контейнера, не абстракції.
- Availability 99.0% (spec §6) — одна невдала генерація звіту не повинна впливати на доступність чату, якщо вони різні контейнери з різним lifecycle.

## Considered options

1. **Лише `backend-service`** — чат, правила, пам'ять і генерація звітів усередині одного сервісу (звіти — внутрішній cron-таск у тому самому процесі); UI чату не описується цією фічею.
2. **`backend-service` + `web-frontend`** — окремий UI-контейнер для чату, але звіти лишаються внутрішнім cron-завданням backend-сервісу.
3. **`backend-service` + `web-frontend` + `worker`** — окремий контейнер для періодичних звітів, незалежний lifecycle від синхронного чат-шляху.

## Decision outcome

**Chosen:** Option 3 — три поверхні: `backend-service`, `web-frontend`, `worker`. UI чату — реальний, уже обіцяний продуктом контейнер, тож `web-frontend` обов'язковий (варіант 1 залишав UI недосказаним). Звіти активності — подієво-часовий, не request/response процес; винесення в окремий `worker` ізолює його lifecycle від latency-критичного шляху чату (варіант 2 ризикує тим, що важка генерація звіту сповільнить синхронний чат в одному й тому ж процесі) і узгоджується з C4-таксономією surfaces.md буквально.

## Consequences

**Positive**
- Latency-цілі чату (§6 NFR) технічно ізольовані від навантаження генерації звітів.
- `worker` може падати/рестартувати незалежно, не зачіпаючи доступність чату (Availability 99.0% легше утримати для критичного шляху).
- UI-контейнер explicit — `api`/`tasks`/`plan-tests` коректно додадуть `ui`-шар задач і component/e2e-тести для чату.

**Negative**
- Три контейнери замість одного — більше деплой-юнітів для однієї людини, що веде розробку (Андрій, ~1-2 год/тиждень); підтримка розкладу воркера — додаткова операційна відповідальність.
- Потрібен спосіб worker'у читати ту саму базу (PostgreSQL, D-59) і ділитись правилами/пам'яттю з backend-service без дублювання логіки.

**Neutral**
- На дуже ранньому етапі (одна людина, MVP) `worker` і `backend-service` можуть тимчасово ділити один процес/деплой (наприклад `node-cron` у тому самому Node-процесі) — контейнерна межа лишається логічною, фізичне розділення відкладається до реального навантаження; це рішення про C4-контейнер, не про фізичний деплой.
