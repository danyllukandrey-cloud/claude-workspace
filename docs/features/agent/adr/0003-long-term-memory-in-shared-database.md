# 0003 — Store long-term agent memory in the shared backend database

- **Status:** Accepted
- **Date:** 2026-08-25
- **Deciders:** Андрій + Клод під час `/sdd:design agent`

## Context

Агент вводить нову чутливу поверхню даних — довгострокову памʼять (US-06/AC-09/AC-15): факти й рішення користувача, збережені між сесіями, можливо разом з іменем, здоров'ям, особистими рішеннями (spec §6.1). Треба вирішити, чи ця памʼять живе в тій самій PostgreSQL-базі, що й картки/Структура (D-59), чи в окремому сховищі — за прецедентом `structure`, де літопис Структури отримав окремий сервіс ([ADR-0004 structure](../../structure/adr/0004-separate-service-for-structure-history-log.md)).

## Decision drivers

- spec §6.1: Security review Required, дані confidential — рішення про сховище прямо впливає на периметр, який Security review має покрити.
- Одна людина веде розробку — нове окреме сховище означає нову інфраструктуру, окремі міграції, окремий бекап-процес.
- На відміну від літопису Структури (append-only подієвий лог, що росте необмежено й читається рідко), довгострокова памʼять читається на **кожному** повідомленні чату (AC-09) — це операційний, не архівний, доступ.

## Considered options

1. **Та сама PostgreSQL-база** — нові таблиці для короткострокового сесійного вікна й довгострокових фактів у тій самій базі, що й картки/Структура.
2. **Окреме сховище памʼяті** — за прецедентом літопису Структури, власний деплой-юніт/схема.

## Decision outcome

**Chosen:** Option 1. Прецедент `structure` (окремий сервіс) виправданий там причиною, якої тут немає: append-only подієвий лог, що зчитується рідко (аналітика), і навмисно ізольований від «джерела правди» карток. Памʼять агента — навпаки, читається на кожному повідомленні в реальному часі (AC-09) і природно повʼязана з тим самим користувачем і тими самими картками, у які пише agent (одна транзакційна межа для запису й памʼяті — AC-02/AC-09 можуть статись в одному повідомленні). Окреме сховище додало б мережевий стрибок на кожен запит без компенсуючої вигоди.

## Consequences

**Positive**
- Один запис і памʼять про цей запис можуть бути однією транзакцією — менше проміжних станів неузгодженості.
- Немає нової інфраструктури — Security review покриває один периметр (уже описаний PostgreSQL-бекенд), не два.

**Negative**
- Чутливі дані (довгострокова памʼять) тепер у тій самій базі, що й оперативні дані карток — модель доступу (RLS/авторизація на рівні рядка) мусить однаково суворо покривати нові таблиці (AC-06), інакше периметр розширюється тихо.
- Немає природної ізоляції «видалити всю памʼять користувача» окремим дропом бази/схеми — видалення (§11 OQ) реалізується як DELETE-запити в спільній базі.

**Neutral**
- Якщо в майбутньому обʼєм довгострокової памʼяті чи вимоги до її окремого шифрування/ретеншену виростуть — міграція в окреме сховище можлива пізніше, ціною окремої SQL-міграції (тижні, не дні — тому це рішення й потребує ADR).
