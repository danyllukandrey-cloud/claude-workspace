## New components

| Component | Why no existing primitive fits | Registered in design-system |
|---|---|---|
| `MessageList` | Прокручуваний список повідомлень чату — жодного list-примітиву для потоку діалогу в інвентарі нема | pending |
| `MessageBubble` | Одне повідомлення (користувача чи агента) — інша природа даних, ніж `CardShell` (не перевертається, не має лицьової/зворотної сторони) | pending |
| `ProposalCard` | Пропозиція запису, що чекає підтвердження, з діями «Підтвердити»/«Уточнити» — специфічно для циклу підтвердження агента (AC-02/AC-02b/AC-03) | pending |
| `Composer` | Поле вводу тексту + прикріплення вкладення + надсилання — `TextField` в інвентарі однорядковий і без прикріплення файлів | pending |
| `RuleCategoryMenu` | Куратоване меню з 6 фіксованих категорій (мультивибір) — інша природа, ніж вільний `TextField` | pending |
| `ReportList` | Список звітів активності зі своїми акцентами (тижневий/місячний/квартальний) і позначкою `dead_letter` | pending |
| `Spinner` | Індикатор завантаження — уже запропонований `structure/screens.md` (та сама конвенція «спінер, не skeleton», `design-system.md`); **reused, не дубльований під новою назвою** | pending (спільний зі `structure`) |
| `Banner` | Інлайн-повідомлення (успіх/помилка/rate-limit/llm-unavailable) — уже запропонований `structure/screens.md` («помилки інлайн, ніколи `alert`/`confirm`»); **reused** | pending (спільний зі `structure`) |
| `EmptyState` | Стандартний порожній стан — уже запропонований `structure/screens.md`; **reused** | pending (спільний зі `structure`) |
| `CardPicker` | Вибір картки з динамічного списку (card-scope правила, AC-12) — той самий компонент, що вже запропонував `structure/screens.md` для вибору цільової картки при перенесенні метрики; **reused** | pending (спільний зі `structure`) |

Усі — `pending`: жоден код компонента ще не написаний ([`design-system.md`](../../design-system.md) — інвентар лише 4 заплановані примітиви). Чотири останні рядки — не нові пропозиції, а той самий компонент, що вже запропонував `structure/screens.md`: продукт отримає **один** реальний компонент кожного виду, коли `implement` вперше його напише, а не два з різними назвами. `implement` реєструє кожен назад в інвентар, коли пише реальний код.
