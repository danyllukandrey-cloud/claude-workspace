## Метод

Незалежні read-only рев'ю-агенти (`sdd:reviewer`) пройшли по всьому diff'у проти `spec.md` §5 (увесь набір AC, не лише те, що згадують трейлери комітів), `sad.md` §6 (послідовності), `data-model.md`, `contracts/openapi.yaml`, `adr/` (зокрема Accepted ADR-0006, sentinel `Result<T,E>`) і `tasks.json` — окремо (stage 1) чи справді працює заявлений AC end-to-end у продакшн-коді, а не лише в юніт-тесті, і (stage 2) якість/конвенції/edge-cases/безпека.

Головний висновок огляду, той самий клас проблеми, що вже траплявся у фічі `structure` ([`../../structure/_review/review-2026-09-11.md`](../../structure/_review/review-2026-09-11.md)): значна частина доменної й app-логіки була написана й повністю юніт-тестована, але жоден рядок production-коду її не викликав («мертва фіча за зеленими тестами») — воркер-крон, запис довгострокової пам'яті, звіт розробнику, гвардія проти карткових перевизначень.

Знахідки згруповані у **11 незалежних задач для виправлення** (файлові групи без перетину, паралельний `Workflow`-запуск, `isolation: 'worktree'` на кожну) + **2 окремі рішення**, винесені на `AskUserQuestion` користувачу до старту фіксів:

1. FK-каскад `agent_audit_event.user_id` при видаленні акаунта (AC-17) — `ON DELETE CASCADE` знищував би журнал аудиту разом з користувачем, чию дію він мав документувати. Користувач обрав `ON DELETE SET NULL`.
2. 4 «великі розриви обсягу», знайдені під час рев'ю (мертва фіча за зеленими тестами): крон воркера, запис AC-09 у довгострокову пам'ять, чат-формулювання правил (AC-14), тригер звіту розробнику (AC-20/AC-20b). Користувач обрав «Доробити зараз» для всіх чотирьох.
