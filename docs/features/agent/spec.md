# Spec — agent

> **Glossary:** [CONTEXT](../../CONTEXT.md)
> **Reference module / docs / channels used:** `PRODUCT-BOOK.md` Блок 4, `Product_Vision.md` §3-5, `design-review.md` Блок 0/2/5-7, `architecture-map.md`, наявний код `plan/app/src/` (лише scaffold-заглушки, коду агента ще нема).

## 1. Context

Зараз користувач не має жодного способу занести подію в картку інакше, ніж вручну заповнюючи форму — а весь продукт (`life-area-card`, `structure`) спроєктований і описаний з розрахунком на «чат з агентом» як основний канал (`Product_Vision.md §5`, `design-review.md` Блок 5-7). Без специфікації Агента цей канал лишається обіцянкою без акцептанс-критеріїв і блокує подальшу реалізацію обох уже спроєктованих фіч.

Актуальність зараз: `life-area-card` і `structure` пройшли повний SDD-конвеєр (spec → design → tasks), а `implement` ще не починався (DELIVERY-PLAN «Розробка» 5%) — саме час зафіксувати поведінку агента, перш ніж писати код, який на нього спирається.

Прийнятий підхід: Агент v1 — єдиний персонаж, що перетворює пряме текстове надходження на запис у картку виключно через явне підтвердження, керується спільним системним промптом (базові правила + меню категорій + власне правило користувача) на дефолтній манері базової LLM, без вибору характеру. Ринкова прогалина (`researcher`, 2026-08-25): жоден з чотирьох знайдених продуктів (MyFitnessPal, ChatGPT Memory, Habit Chat, Memex) не поєднує підтвердження-перед-записом + гібридну пам'ять + власні правила поведінки в одному домен-незалежному агенті. Найгостріший ризик (`devils-advocate`, 2026-08-25): механізм примусу власного правила користувача не спроєктований (D-35) — тихе порушення не буде виявлене чи залоговане. Тому специфікація нижче розводить AC «запис» і AC «дотримання правила» окремо (§5), а сам механізм примусу йде у відкриті питання (§8) з власником Андрієм, не мовчазним припущенням.

Джерела: `Product_Vision.md §3-5`, `PRODUCT-BOOK.md` Блок 4, `design-review.md` Блок 0/2/5, рішення D-25, D-26, D-27, D-30, D-31, D-35, D-37, D-41, D-43, D-54.

## 2. Goals

- Перетворювати будь-яке пряме текстове надходження користувача на коректний запис у потрібній картці — завжди з підтвердженням перед записом.
- Дотримуватись правил користувача (базове меню категорій + власне сформульоване правило) на кожній відповіді агента.
- Пам'ятати користувача гібридно між сесіями — не втрачати щойно сказане до того, як воно стало рішенням.

## 3. Non-goals

- Голосове розпізнавання/синтез — окрема технічна частина (D-41); ця специфікація описує лише поведінку агента після того, як текст уже отримано.
- Вибір «характеру» агента (мовчазний консультант/друг/мотиватор, D-37) — відкладено на майбутню версію; v1 працює на дефолтній манері базової LLM.
- Готові інтеграції зовнішніх конекторів — вже Non-goal `life-area-card/spec.md`, не дублюється тут.
- Проактивна ініціатива й нагадування — виключено D-31/D-43, не в цій версії.

## 4. User stories

### US-01: Запис вільним текстом
**As a** user
**I want** описати подію своїми словами
**So that** агент оновить потрібну картку без заповнення форми

### US-02: Підтвердження перед записом
**As a** user
**I want** щоб агент завжди перепитав перед записом
**So that** невірно розпізнане повідомлення ніколи мовчки не змінить мої дані

### US-03: Власне імперативне правило
**As a** user
**I want** задати власне правило, якого агент завжди дотримується («не радь, якщо не питаю»)
**So that** агент поводиться так, як хочу саме я, а не за загальним дефолтом

### US-04: Правило з готового меню
**As a** user
**I want** обрати готові категорії правил, а не писати все з нуля
**So that** я можу швидко задати межі, не знаючи, як точно сформулювати імперативне правило

### US-05: Виправлення помилки вводу
**As a** user
**I want** щоб агент пояснив, що не так, коли я ввів суперечливі дані
**So that** я виправлю це одразу, а не виявлю зіпсоване число тижні по тому

### US-06: Пам'ять між сесіями
**As a** user
**I want** щоб агент пам'ятав те, що я вже казав раніше, без повторів
**So that** я не почуваюсь так, ніби щоразу розмовляю з незнайомцем

### US-07: Розпізнавання правильної картки
**As a** user
**I want** щоб агент сам зрозумів, до якої картки належить повідомлення
**So that** мені не треба щоразу явно називати картку

## 5. Acceptance criteria

### AC-01 (US-01) — happy path
**Given** користувач має активну картку й описує подію вільним текстом
**When** повідомлення надіслано
**Then** агент визначає ймовірну картку й метрику та пропонує конкретний запис, перш ніж щось зберегти

### AC-02 (US-02) — happy path
**Given** агент запропонував конкретний запис і чекає на відповідь
**When** користувач підтверджує
**Then** система записує подію в картку і показує користувачу, що це збережено

### AC-03 (US-02) — domain invariant
**Given** агент запропонував запис
**When** користувач явно не підтвердив (мовчить або пише щось не по темі)
**Then** система нічого не записує — мовчазного запису не буває

### AC-04 (US-05) — error
**Given** користувач вводить дані, які суперечать уже відомому, або повідомлення, яке не мапиться на жодну відому метрику
**When** агент це помічає
**Then** агент пояснює простими словами, що саме незрозуміло чи суперечливо, і просить уточнити — не вгадує і не мовчить

### AC-05 (US-07) — cross-context
**Given** повідомлення користувача могло б стосуватись кількох наявних карток або жодної
**When** агент намагається визначити, куди його записати
**Then** агент питає користувача, яку картку мав на увазі, або пропонує створити нову — не вгадує сам

### AC-06 (US-01) — authorization
**Given** користувач автентифікований через Google-вхід
**When** агент читає чи записує будь-які дані картки
**Then** система обмежує кожну дію лише картками й Структурою саме цього користувача — навіть якщо в тексті згадано чиєсь інше ім'я чи дані

### AC-07 (US-03) — happy path
**Given** користувач задав власне імперативне правило («не радь, якщо не питаю»)
**When** виникає ситуація, де базова модель за замовчуванням дала б непрохану пораду
**Then** відповідь агента слідує правилу користувача, а не дефолтній поведінці

### AC-08 (US-04) — happy path
**Given** користувач відкрив налаштування правил
**When** обирає одну чи кілька категорій з готового меню, без вільного тексту
**Then** система зберігає обрані категорії як активні правила, і подальші відповіді агента їх відображають

### AC-09 (US-06) — happy path
**Given** користувач у попередній сесії повідомив значущий факт чи рішення
**When** пізніша сесія торкається тієї самої теми
**Then** відповідь агента враховує цей факт без повторного пояснення від користувача

## 6. Non-functional requirements

## 6.1 Security / privacy

- **Data classification:** confidential — особисті дані про життя користувача (картки, факти, рішення).
- **Personal data touched:** так — текст повідомлень, довгострокові факти в пам'яті агента (можуть включати ім'я, здоров'я, рішення) — нова чутлива поверхня даних.
- **AuthZ/AuthN impact:** кожен запит прив'язаний до автентифікованої сесії (Google-вхід, D-33); усі читання/записи скеровані лише на Структуру й картки цього користувача (AC-06).
- **Abuse cases:**
  - крос-користувацький доступ до чужих карток → блокується на рівні бекенда (AC-06)
  - отруєння/невидалюваність довгострокової пам'яті (правдоподібна хибна теза потрапляє в пам'ять і незвідки видалити) → механізм редагування/видалення не спроєктований — §8
  - спам-записи → ліміт частоти на бекенді, конкретне число не вирішено — §8
  - injection через текст повідомлення/вкладення, що намагається змусити агента порушити власні чи базові правила → агент лишається в межах системного промпту ПЛАНу незалежно від вмісту вхідного тексту
- **Security review:** Required — нова фіча M-розміру з новою чутливою поверхнею даних (довгострокова пам'ять).

## 7. Metrics / KPIs

- **Частка записів через чат, підтверджених без виправлення** — baseline: 0 (нова фіча), target: ≥80% протягом перших 30 днів використання.
- **Медіанний час від повідомлення до підтвердженого запису** (весь цикл AC-01→AC-02) — baseline: невідомо, target: ≤10 секунд медіанно, вимірюється протягом 90 днів після запуску.
- **Частка повідомлень, де агент правильно визначив картку без уточнюючого питання** (AC-05) — baseline: невідомо, target: ≥90%, вимірюється протягом 90 днів після запуску.
