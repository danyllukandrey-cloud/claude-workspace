# 0004 — Run the Structure history log as a separate deployable service

- **Status:** Accepted
- **Date:** 2026-08-24
- **Deciders:** Андрій Данилюк (з Клодом під час Socratic-проходу `design`)

## Context

AC-15 вимагає, щоб перейменування картки й переміщення в розкладці «за логікою» записувались як подія літопису Структури з часовою міткою — той самий механізм, що вже записує закриття (AC-12). D-39 фіксує: запис іде з першого дня, окремий екран перегляду — поза цією версією продукту. У цій сесії Андрій свідомо обрав винести запис цього літопису в окремий деплой-юніт — другий сервер поруч із уже наявним мінімальним бекендом (D-24) — замість таблиці/модуля всередині нього.

## Decision drivers

- Явний вибір власника фічі (Андрій, під час цього Socratic-проходу) — тримати літопис Структури окремо від решти мінімального бекенда.
- Продукт передбачає майбутнє розширення цього сервісу (наступна версія: перегляд літопису, розклад автоматичних звітів) — за межами v1, але напрямок уже названий.

## Considered options

1. **Окрема таблиця/модуль усередині вже наявного мінімального бекенда (D-24)** — жодного нового деплой-юніту, той самий сервер веде і Структуру, і картки, і літопис.
2. **Окремий деплой-юніт спеціально для літопису Структури** — власний сервіс, який приймає події від мінімального бекенда й пише їх у власне сховище.

## Decision outcome

**Chosen:** Option 2, свідомо, за прямим вибором власника фічі. Це відхилення від конвенції, яку зафіксував D-24 («мінімальний бекенд» — одна служба на дві задачі) і яку вже використовує затверджений `sad.md` `life-area-card` (§5: «конкретна структура папок серверного коду ще не встановлена... бекенд жодного разу не піднімався»). Explicitly обране Андрієм: другий сервер існує спеціально під майбутнє розширення літопису (перегляд, автозвіти) — не для самого MVP-обсягу запису подій, який сам собою обійшовся б варіантом 1. Будь-яка майбутня участь агента в цьому сервісі — предмет окремої фічі `agent` (D-56) і окремого рішення, не цього ADR.

## Consequences

**Positive**
- Межа відповідальності чітка з першого дня: сервіс літопису ніколи не обробляє нічого, крім подій Структури — легше рости в бік майбутніх звітів без зачіпання решти бекенда.
- Відхилення від D-24 зафіксоване явно тут, а не мовчки — наступний, хто читає код, бачить причину.

**Negative**
- Другий деплой-юніт для одноосібного проєкту в темпі ~1–2 год/тиждень (sad.md §2) — окремий хостинг, окремий запуск, окремий моніторинг, коли й мінімальний бекенд (D-24) ще жодного разу не піднімався. Це технічний борг/ризик, зафіксований у sad.md §11.
- Синхронний виклик мінімальний-бекенд → сервіс-літопису додає точку відмови: якщо сервіс літопису недоступний, запис події (AC-15) або блокується, або губиться — конкретна поведінка при недоступності визначається на `data-model`/`tasks`, тут не вирішена.

**Neutral**
- Якщо майбутнє розширення (перегляд, автозвіти) не відбудеться найближчим часом, окремий сервіс якийсь час робитиме лише те, що спокійно вмістилось би в одну таблицю мінімального бекенда — прийнятна ціна за раннє розділення меж.
