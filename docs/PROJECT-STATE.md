  Гіпотеза про різні версії застосунку виявилась **хибною**. Справжня причина:
  у застосунку Claude існує **два види Проєктів**.

  | Вид | Природа | Синхронізація |
  |---|---|---|
  | **Хмарні** | живуть на серверах, прив'язані до акаунту | автоматично, скрізь однакові |
  | **Локальні** (мітка «локал») | проєкти Cowork, прив'язані до **папки на конкретному ПК** | **не синхронізуються — і не мають** |

  **Доказ:** у браузері на обох ПК списки Проєктів **збігаються**. Отже хмара і акаунт
  у порядку. Розбіжність дає лише локальний шар.

  **Чому локальні не синхронізуються — за природою, не через баг:** локальний проєкт
  містить шлях типу `C:\Users\U\Desktop`. На другому ПК профіль інший (`C:\Users\Andrii\`),
  і цей шлях там або не існує, або веде в інше місце. Переносити адресу папки
  між комп'ютерами безглуздо.

  **Практичний висновок:** локальний проєкт **не переносять — його створюють заново**
  на кожному ПК і наводять на локальну копію папки. Однаковим зміст робить **Git**,
  а не Проєкт.
- **Синхронізація файлів:** тему хмарних сховищ (Google Drive / OneDrive / Syncthing /
  Git) обговорено, але рішення **не ухвалено**. Андрій сказав: «Ми так робити все одно
  не будемо». Метод синхронізації — **відкрите питання**.
- **Розбіжність імен користувача:** на паралельному ПК шлях `C:\Users\Andrii\...`,
  на поточному — `C:\Users\U\...`. Це різні профілі Windows, що важливо враховувати:

### 10.1 Головна ідея, яка прямо стосується нашої задачі

Формулювання з Модуля 6: **«чому файли, а не пам'ять сесії»**.

Інформація живе у **файлах-артефактах** (`CONTEXT.md`, `idea-brief.md`, `PRD.md`,
`sad.md`, `data-model.md`, OpenAPI, `tasks/`), а не в пам'яті чату. Skills (навички —
готові сценарії для Claude Code) проводять автора по фазах від ідеї до атомарних задач.

Це **відповідь на твоє початкове питання** про роботу з різних пристроїв: єдина система
досягається не синхронізацією чатів, а тим, що весь стан проєкту лежить у файлах у Git.
Сесія може згоріти, комп'ютер змінитися — артефакти лишаються.

### 10.3 Модуль 6 — SDLC toolkit (найважливіший для «ПЛАНу»)

SDLC = Software Development Life Cycle (життєвий цикл розробки).

**Лекції:**

| Лекція | Тема | Інструмент |
|---|---|---|
| 6.1 | SDLC через артефакти — мапа фаз і гейтів | `00-overview/` |
| 6.2 | Gate 1: словник домену → idea-brief | `fix-term`, `interview`, `classify-size` |
| 6.3 | PRD | `write-prd` |
| 6.4 | Architecture Design — arc42 + ADR + C4 | `architecture-design`, `decide-adr` |
| 6.5 | Sequence diagrams + модель даних | `complete-sequence-diagrams`, `generate-data-model` |
| 6.6 | API-контракти (OpenAPI) | `api-forge` |
| 6.7 | Задачі | `break-tasks`, `plan-tests` |

**Розшифровка термінів:**
- **PRD** — Product Requirements Document, документ вимог до продукту.
- **SAD / arc42** — Software Architecture Document, опис архітектури за шаблоном arc42 (12 секцій).
- **ADR** — Architecture Decision Record, запис архітектурного рішення: що вирішили і чому.
- **C4** — спосіб малювати архітектуру на 4 рівнях деталізації (Context / Container / Component / Code).
- **Gate** — «ворота»: контрольна точка, яку не можна пройти, поки попередній документ не готовий.
- **Slug** — коротка назва фічі в kebab-case, напр. `goals-tracking`.

**Три способи використати toolkit:**
1. Як plugin: `claude --plugin-dir ./plugin` → команди `/sdlc-interview`, `/sdlc-write-prd` тощо.
2. Скопіювати шаблони руками у свій репозиторій (`document-templates/`, `plugin/skills/*/templates/`).
3. Як reference для домашки.

**Приклади в репо** (синтетичні): `course-lesson-mvp` (наскрізний, повний ланцюжок),
`goals-tracking` (arc42 для модуля з OKR-логікою — **тематично найближчий до «ПЛАНу»**),
`rate-limiting`.

### 10.4 Skill `interview` — перший крок будь-якої фічі

Прочитаний повністю. Це 14-фазний протокол створення `idea-brief.md` (15 секцій, ≤5 сторінок).

Ключове:
- Фази 0–11 — **read-only** (нічого не пишеться на диск), лише на фазі 12 створюється файл.
- Фази 1, 2, 9, 10, 11 — **обов'язкові питання користувачу**. Вигадувати за користувача
  відповіді заборонено: «фабрикація = artifact NOT DoD-valid».
- Claude сам робить конкурентний аналіз (фаза 4), генерує 3 стратегічні підходи
  (Simplicity / Differentiation / Balanced — фаза 5), проводить рев'ю з 3 позицій
  (Інженер / Керівник / UX — фаза 6) і «адвоката диявола» (фаза 8).
- **RICE** (Reach × Impact × Confidence / Effort — формула пріоритизації) рахує Claude,
  користувач лише підтверджує або коригує. Явна анти-практика — «гра в калькулятор»,
  коли числа питають у користувача.
- Окрема вимога від 2026-05-23: усі питання формулюються **українською, junior-friendly**,
  з розшифровкою термінів і прихованих компромісів. Це збігається з твоїм стилем роботи.

### 10.5 CONTEXT.md за методологією курсу

Курс має **власний шаблон `CONTEXT.md`**, і він **вужчий** за цей файл. За курсом
`CONTEXT.md` = **словник домену**, а не загальний контекст:

```
## Glossary     — термін · визначення в 1 речення · межа (чим НЕ є)
## Invariants   — правила домену, що діють завжди
## Out of scope — що явно НЕ наш контекст
```

Явна заборона в шаблоні: **жодних технічних деталей** (без Redis/Postgres, назв
бібліотек, API-контрактів). Тільки слова домену і межі між ними.

⚠️ **Розбіжність:** цей файл (`CONTEXT.md`, який ти зараз читаєш) — НЕ за курсовим
шаблоном. Він робочий і ширший. Коли зводитимемо простори, треба вирішити: перейменувати
цей файл (напр. на `PROJECT-STATE.md`), а `CONTEXT.md` залишити під словник домену за
курсом. Інакше буде плутанина з інструментами курсу.

### 10.6 DoR / DoD (гейти якості)

**Definition of Ready** — що має бути готове ДО першого рядка коду: SPEC із критеріями
приймання у форматі Given/When/Then, схвалена архітектура, C4, зафіксований API-контракт,
модель даних + план міграції та відкату, ADR-и, розбиття на задачі ≤1 дня, план тестів,
план викочування. Якщо хоч один пункт не закритий — повертаємось на попередню фазу.
Для XS/S-задач частину можна пропустити, але з явним «N/A».

**Definition of Done** — коли фіча вважається готовою: усі задачі закриті, тести за
планом і CI зелений, міграція виконана на staging і відкат перевірений, OpenAPI оновлений,
ADR оновлений якщо рішення змінилось, запис у CHANGELOG, нотатка в базу знань,
логи/метрики/алерти, оновлена документація.

Не є DoD: увімкнений feature flag у проді, 100% покриття тестами, анонс у Slack.

### 10.7 Модуль 3 — 4 рівні захисту

1. **Settings** — три файли: `~/.claude/settings.json` (глобальний), `.claude/settings.json`
   (проєктний, у git), `.claude/settings.local.json` (особистий, у gitignore).
2. **Permissions** — `allow` / `deny`. Deny блокує читання `.env`, `*.pem`, `*.key`,
   `~/.ssh`, `~/.aws`.
3. **Sandbox** — захист на рівні ОС; bash не прочитає файл, навіть якщо сам bash дозволений.
   `network.allowedDomains` — білий список доменів.
4. **Devcontainer** — firewall на рівні ОС, default-deny.

### 13.2 Конвеєр SDD (порядок обов'язковий)

**Крок 0 — один раз на репозиторій:**
`/sdd:survey` — на існуючому коді сканує й пише `docs/architecture-map.md`; на порожньому

**Хребет (по черзі):**
`specify` → `clarify` → `design` → `sequences` → `data-model` → `api` → `tasks` →
`plan-tests` → `implement`

**Замикання циклу:** `review` → `ship`

**Утиліти (будь-коли):** `interview` (стрес-тест сирої ідеї), `classify-size` (XS…XL),
`glossary` (термін у `CONTEXT.md`), `decide-adr`, `fix` (вхід для багфіксів)

### 13.3 Стан Андрія — усе узгоджено

`SETUP_DONE.md` фіксує наявність `docs/architecture-map.md`, 3 ADR і `tasks.json`.
Це **точно вихід `/sdd:survey` у greenfield-режимі**. Отже крок 0 пройдено, і записаний
наступний крок `/sdd:specify` — коректний.

### 13.4 Три правила, які легко порушити

1. **`/clear` між етапами обов'язковий.** Кожен етап заново читає входи з диска —
   переносити контекст не треба і шкідливо. Виняток: петля `review` → `implement`.
2. **Регулятор глибини** `--depth=easy|medium|hard`. Змінює кількість питань, не покриття.
   `hard` вмикає повний аналіз: конкуренти, 3 стратегічні підходи, адвокат диявола.
   Дефолт задається ключем `interview_depth` у `.claude/sdd.local.md`.
3. **Відмова етапу — не помилка**, а вказівка, який крок пропущено.

### 13.5 Конфіг `.claude/sdd.local.md`

Створюється автоматично при першому запуску, самодокументований, потрапляє в `.gitignore`
(бо персональний). Ключі: `interview_depth`, `tdd`, `team_mode`, `workflow_mode`,
`max_parallel_agents`, `isolation`, `auto_commit`, `branch_strategy`, моделі й effort
по ролях, `dashboard_enabled`.
