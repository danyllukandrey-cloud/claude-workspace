# DECISIONS — реєстр рішень проєкту «ПЛАН»

Одне місце, де видно **всі ухвалені рішення**: що діє, що відкладено і за якою умовою до відкладеного повертаємось.

## Як цим користуватись

**Це індекс, а не сховище.** Тут — короткий рядок і посилання. Повний контекст живе там, де він уже написаний: `PROJECT-STATE.md`, `docs/adr/`, брифи фіч.

**Чому саме так.** 2026-07-22 ми зловили суперечність: рішення про `portfolio-rebalance` жило і в `SETUP_DONE.md`, і в `PROJECT-STATE.md` — копії розійшлися, і документи почали казати різне. Дублювати текст рішень ще раз — повторити ту саму помилку. Тому тут тільки покажчик.

**Правило:** ухвалив рішення → допиши рядок сюди + деталі туди, де вони доречні. Передумав → зміни статус тут і додай примітку там. Не редагуй минуле мовчки.

**Який номер брати наступним.** Таблиця не відсортована (D-20 стоїть перед D-19), тому «подивитись на останній рядок» дає неправильну відповідь. Рахуй максимум:

```powershell
Select-String docs\DECISIONS.md -Pattern '^\| D-(\d+) \|' | ForEach-Object { [int]$_.Matches.Groups[1].Value } | Sort-Object | Select-Object -Last 1
```

Якщо номер знадобився вже під час коміту — хук `.githooks/commit-msg` друкує наступний вільний просто в тексті помилки, рахувати не треба.

> **Пастка двох комп'ютерів.** Узяв номер тут, а на другому ПК без `git pull` узяв той самий — і два різні рішення під одним номером. Захист той самий, що й від решти розбіжностей: `git pull` **перед** роботою.

## Статуси

| Статус | Значення |
|---|---|
| **діє** | рішення ухвалене й виконується |
| **відкладено** | свідомо не робимо зараз; є тригер повернення |
| **скасовано** | рішення скасоване новим; лишається в історії, щоб не ходити по колу |
| **відкрито** | питання поставлене, відповіді ще немає |

## Відкладене — що чекає й чого саме чекає

Найважливіша частина документа. Якщо тут порожньо — або все зроблено, або ми щось забули записати.

### D-85 · Незалежний конектор з 1-ї хвилини + джерело факту для аналітики

**Стан:** конектори (Google Fit, Apple Health тощо) — поза v1 у `life-area-card/spec.md` і `agent/spec.md` Non-goals, місце закладено (`idea-brief.md §5`). Поведінка картки при конфлікті ручного вводу з даними конектора вже спроєктована (design-review Блок 6), активується лише з першим реальним конектором. `structure/spec.md §8` окремо фіксує той самий розрив на рівні довіри до аналітики: «розрив і прогрес спираються лише на дані, які сам користувач вносить; системі нема з чим звірити це ззовні».

**Чому відкладено:** немає реальних користувачів чи даних, які виправдали б вартість першого конектора зараз; ризик приймається свідомо — так само, як уже зафіксовано в `idea-brief.md §10`.

**Тригер повернення:** коли з'явиться перший реальний конектор.

**Перший крок, коли повернемось:** активувати вже спроєктовану поведінку конфлікту ручного вводу з даними конектора (design-review Блок 6) на першому реальному прикладі (Google Fit чи Apple Health).

### D-86 · Юніт-економіка голосового каналу (Q-11)

**Стан:** голосова розмова (D-41) витрачає оплачуваний виклик Claude API в рази швидше за текст — найактивніший користувач стає найдорожчим. Тарифікація (за результат чи за спожите) і ліміти не вирішені.

**Чому відкладено:** продукт зараз для одного користувача (Андрія) — немає реальних даних про використання, щоб обґрунтовано порахувати ліміти чи тарифи.

**Тригер повернення:** перед виходом продукту за межі одного користувача.

**Перший крок, коли повернемось:** зібрати фактичні дані витрат голосових реплік Андрія за період використання як базову лінію для розрахунку.

### D-87 · Темп розробки vs обсяг онбордингу

**Стан:** ризик адвоката диявола спирався на оцінку ~75 год/рік (1-2 год/тиждень) з `idea-brief.md §10` — Андрій підтверджує, що фактичний темп значно вищий, оцінка застаріла.

**Чому відкладено:** обґрунтованої відповіді на застарілих вхідних даних не дати; текст `idea-brief.md` не переписуємо заднім числом (D-46) — виправлення прийде природно через повторний прохід інтерв'ю.

**Тригер повернення:** повторний прохід `sdlc-interview` з актуалізованою оцінкою темпу розробки.

### D-12 · Docker Desktop і реальний запуск контейнера

**Стан:** файли Рівня 4 (`.devcontainer/`, `docker-compose.yml`) у репозиторії, перевірені статично. Контейнер жодного разу не запускався.

**Чому відкладено:** (1) на поточному етапі навчання це занадто складно — свідомо спрощуємо; (2) ПЛАН — клієнтський застосунок, контейнер йому не потрібен; Docker тут лише для ізоляції агента.

**Тригер повернення:** поява автономного агента, що працює довго й без нагляду.

**Термінологічна межа:** це рішення — виключно про мережеву ізоляцію самого Claude Code (агента розробки, firewall навколо контейнера). NOT база даних застосунку ПЛАН — та йде окремим рішенням [ADR-0005](adr/0005-backend-datastore.md) і Docker Desktop не потребує взагалі ([ISS-12](ISSUES.md)). NOT продакшн-деплой готового коду — це третя, ще не ухвалена тема (курс, модуль 11.2, інший Docker Compose для іншої мети).

**Перший крок, коли повернемось:** `(Get-CimInstance Win32_ComputerSystem).HypervisorPresent` → має бути `True`. Далі — покроково у [PROJECT-STATE §13.10](./PROJECT-STATE.md).
