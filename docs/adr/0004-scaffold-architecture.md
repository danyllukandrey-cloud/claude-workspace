# ADR-0004: Архітектура каркасу — шари всередині картки, корінь коду в `plan/app/`

- Статус: Accepted (підтверджено Андрієм 2026-08-07)
- Дата: 2026-08-07

## Контекст

Настав момент матеріалізувати проєкт у файлову систему: створити каркас (scaffold) —
структуру папок і базові файли, ще без робочого коду.

Дві вимоги стикаються.

**Перша — від уроку 4.10 курсу.** У проєкті має бути **явно записане правило залежностей**
(dependency rule): хто кого має право імпортувати. TypeScript, на відміну від Go, не вміє це
перевіряти сам — у Go пакети під `internal/` фізично неможливо імпортувати ззовні модуля, а в
TypeScript немає нічого подібного. Тому правило існує лише настільки, наскільки воно написане
словами. Якщо його не написати, Claude порушить його ненавмисно.

**Друга — від [ADR-0002](./0002-card-module-architecture.md).** Він уже вирішив, що картка —
самодостатній модуль: одна папка на картку, спільне окремо. І він **явно розглянув і відхилив**
групування за технічним типом («всі компоненти в `components/`, вся логіка в `logic/` — класичний
layered підхід»).

Класична подача Clean Architecture — це верхньорівневі папки `domain/`, `application/`,
`infrastructure/`, `presentation/`. Це буквально той варіант, який ADR-0002 відхилив. Тобто
взяти Clean «як у книжці» = мовчки скасувати чинне рішення.

Додатковий контекст: код вирішено класти в `plan/app/`, тоді як `architecture-map.md`,
ADR-0002, ADR-0003 і `tasks.json` писалися з розрахунку на `src/` у корені репозиторію.

## Розглянуті варіанти

**1. Layered (шарова).** `UI → Business → Data`, три верхніх папки.
Просто і швидко. Але це рівно те, що ADR-0002 відхилив, і при зростанні кількості карток
логіка різних карток перемішується в одній папці `Business`.

**2. Clean Architecture верхньорівневими шарами.** `domain/`, `application/`,
`infrastructure/`, `presentation/` у корені `src/`.
Канонічна форма, найближча до букви уроку. Мінуси: одна картка виявляється розрізаною по
чотирьох папках, тобто щоб зрозуміти одну картку, треба відкрити чотири місця. Скасовує ADR-0002.

**3. Шари всередині картки (гібрид).** Картка лишається однією папкою `src/cards/<slug>/`, а
всередині неї — `domain/` (правила) і `ui/` (React).
Мінус: це не канонічна подача, і в підручнику такої картинки немає — доведеться пояснювати
кожному новому учаснику.

## Рішення

**Обрано варіант 3.** Плюс до нього: **корінь коду — `plan/app/`**.

Структура:

```
plan/app/src/
  cards/<slug>/
    domain/      чисті правила картки — без React, без localStorage, без Tailwind
    ui/          React-компоненти картки
    index.ts     публічний вхід: що з картки видно назовні
  shared/
    ui/          спільні примітиви: CardShell, Button, NumberField
    storage/
      port.ts    інтерфейс сховища — ЩО картці потрібно
      local.ts   реалізація через localStorage — ЯК це зроблено
    priority/    заготовка на майбутнє, у MVP не будуємо
  app/           точка входу, реєстрація карток, підстановка реалізацій у порти
```

Правило залежностей (стрілка = «має право імпортувати»):

```
ui       →  domain                   вигляд знає правила
domain   →  НІЧОГО                   ні React, ні localStorage, ні Tailwind
domain   →  shared/storage/port.ts   виняток: тільки інтерфейс, ніколи не local.ts
app      →  cards, shared            app склеює: підставляє local.ts у port.ts
картка   →  картка                   ЗАБОРОНЕНО. Тільки через shared/ або app/
```

## Обґрунтування

**Clean Architecture — це напрямок залежностей, а не назви папок.** Урок 4.10 каже це прямо:
«Clean Architecture гнучка — структуруй під свій проєкт». Суть правила — головна логіка не
знає про фреймворк і про спосіб зберігання даних. Варіант 3 виконує цю суть повністю: у
`domain/` немає жодного імпорту React чи `localStorage`.

**Обидві вимоги виконані одночасно.** Правило залежностей записане явно (вимога уроку), картка
лишається однією папкою (рішення ADR-0002). Скасовувати нічого не треба.

**Це усталена практика фронтенду, а не імпровізація.** Публічні рекомендації сходяться на тому,
що для React базою має бути папка на фічу, а шари вводяться всередині фічі: фіча лишається
цілісною і видаляється однією дією.

**`port.ts` окремо від `local.ts` — це і є інверсія залежностей.** Картка каже «мені потрібно
зберегти дані» (`port.ts`), не знаючи, хто саме зберігає. Коли з'явиться бекенд, поруч ляже
`http.ts`, і жодну картку не доведеться переписувати. Це прямо продовжує
[ADR-0003](./0003-client-only-persistence.md), який заклав шар абстракції над `localStorage`.

**Чому не варіант 2.** Ціна — розрізана картка й скасований ADR-0002 — не окупається. Виграш
був би лише в тому, що структура впізнається з підручника.

## Наслідки

- **ADR-0002 лишається чинним.** Цей ADR його **уточнює**, а не скасовує: додає шари всередині
  папки картки. Рішення «картка = одна самодостатня папка» діє далі.
- **Шляхи в ADR-0002 і ADR-0003 читаються від `plan/app/`.** Тобто `src/cards/<slug>/` у тих
  документах означає `plan/app/src/cards/<slug>/`. Самі ADR не редагуємо — це записи історії.
- **Конвенція в `architecture-map.md` оновлена:** було «картка = папка з `Card.tsx` + `logic.ts`»,
  стало «папка з `domain/` + `ui/` + `index.ts`».
- **Правило залежностей дублювати не можна.** Воно живе в одному місці —
  `plan/app/CLAUDE.md`. `ARCHITECTURE.md` на нього посилається, а не переписує.
- **Перевірки правила немає.** TypeScript його не enforce-ить. Якщо порушення почнуть
  траплятись, наступний крок — ESLint-правило `no-restricted-imports`. Поки що це свідомо
  не робимо: інструмент без потреби.
- **Ціна вибору:** структура не збігається з підручниковою картинкою Clean Architecture. Для
  здачі домашнього завдання це треба пояснити одним реченням.
