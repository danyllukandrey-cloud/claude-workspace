# ADR-0005: База даних мінімального бекенда — PostgreSQL

- Статус: Accepted (підтверджено Андрієм 2026-08-23)
- Дата: 2026-08-23

## Контекст

[D-24](../DECISIONS.md#d-24) (2026-08-16) увів мінімальний бекенд — сервер-проксі для Claude API, синхронізації даних між пристроями й Google-входу. `localStorage` став локальним кешем, а «джерело правди» переїхало на сервер. Але саму технологію бази даних на цьому сервері жодне рішення не фіксувало — [ADR-0003](./0003-client-only-persistence.md) згадує PostgreSQL/SQLite лише як відхилений варіант із первинної версії рішення (2026-07-02), коли бекенда не було взагалі.

Прогалину виявив скіл `/sdd:data-model` під час роботи над першою фічею (`life-area-card`, [D-56](../DECISIONS.md#d-56)) — без обраної технології писати реальні SQL-міграції нема на чому.

## Розглянуті варіанти

**1. PostgreSQL.** Реляційна СУБД, стандартний вибір для вебзастосунків цього типу. Структуровані дані (картки, записи, статуси pending/confirmed/rejected — ADR life-area-card 0002) добре лягають у таблиці зі зв'язками. Безкоштовні хостинги для MVP (Supabase, Neon, Render) знімають турботу про власний сервер БД.

**2. SQLite.** Один файл, найпростіше підняти для одного розробника. Гірше пасує задачі синхронізації між пристроями (D-24) — файлова база не розрахована на паралельний доступ з кількох клієнтів так природно, як клієнт-серверна СУБД.

**3. Не обирати зараз (TBD).** Відкласти рішення, дублювати відкрите питання в кожній наступній фічі, що торкається бекенда (`life-area-card`, майбутні `structure`, `agent`) — obviously гірше: кожна фіча наштовхнеться на ту саму прогалину.

## Рішення

**Обрано варіант 1 — PostgreSQL.**

## Обґрунтування

- Дані картки (D-24, D-57) — структуровані, зі зв'язками (картка → записи → статуси), природно лягають у реляційну модель.
- Синхронізація між пристроями (D-24) і конкурентні записи (life-area-card ADR-0002, статус `pending`) потребують клієнт-серверної СУБД з нормальним керуванням конкурентним доступом — сильна сторона PostgreSQL, слабка для SQLite.
- Безкоштовні хостинги (Supabase, Neon, Render) дають готову PostgreSQL-базу без потреби адмініструвати сервер — узгоджується з обсягом one-person MVP.
- Широка підтримка інструментів міграцій (будь-який SQL-based мігратор) — не звужує майбутній вибір фреймворку бекенда.

## Наслідки

- `architecture-map.md` оновлюється: додається технологія бази бекенда (раніше — просто «база на бекенді», без назви) і новий розділ `§Migrations` з інструментом-заглушкою (конкретний інструмент міграцій — коли бекенд вперше scaffold-иться).
- `docs/features/life-area-card/data-model.md` і його SQL-міграції спираються на це рішення — Postgres-синтаксис, не generic SQL.
- **Ціна вибору:** потрібен хостинг PostgreSQL навіть для MVP (хай і безкоштовний рівень) — трохи більше налаштувань, ніж один файл SQLite.
- Не фіксує конкретний ORM/query-білдер чи фреймворк бекенда — це окреме рішення, коли бекенд вперше піднімається.
