# ARCHITECTURE.md — застосунок «ПЛАН»

Одна сторінка: яка архітектура, куди класти новий код, де межі.

## Що це

Застосунок з **generic-карткою** (D-23) — один код, кожна картка користувача (здоров'я,
навчання, кар'єра…) це лише інші дані того самого механізму. Картка має лицьову сторону
(Опис + Дані) і зворотну (Відстеження — тільки числа). Текстова аналітика й чат живуть на
рівні застосунку, не на окремій картці.

> ⚠️ **Оновлено 2026-08-16 (D-23, D-24).** «Бекенду немає» більше не так — з'явився
> мінімальний бекенд (проксі для Claude API, синхронізація, Google-вхід). Дані картки й далі
> насамперед клієнтські: `localStorage` тепер кеш (~2 МБ), бекенд — джерело правди для
> синхронізації. Деталі — [`design-review.md`](../features/life-area-card/design-review.md).

## Архітектурний стиль

**Шари всередині картки.** Картка лишається однією самодостатньою папкою, але всередині
розділена на правила й вигляд.

Це гібрид: базова одиниця — фіча (рішення [ADR-0002](../../docs/adr/0002-card-module-architecture.md)),
напрямок залежностей — за Clean Architecture (рішення [ADR-0004](../../docs/adr/0004-scaffold-architecture.md)).

Класичних верхньорівневих папок `domain/ application/ infrastructure/ presentation/ ` тут
свідомо **немає**: вони розрізали б одну картку на чотири місця.

## Правило залежностей

Живе в одному місці — [`CLAUDE.md`](./CLAUDE.md), розділ «Правило залежностей».
Тут не дублюємо, щоб копії не розійшлися.

Коротко суть: `domain` картки не знає ні про React, ні про спосіб зберігання даних.

## Де що живе

| Папка | Що там | Правило |
|---|---|---|
| `src/cards/<slug>/domain/` | типи предметної області, чисті функції розрахунку, валідація | без React, без `localStorage` |
| `src/cards/<slug>/ui/` | React-компоненти картки | знає свій `domain`, не знає чужих карток |
| `src/cards/<slug>/index.ts` | публічний вхід картки | єдина точка, через яку картку видно назовні |
| `src/shared/ui/` | `CardShell`, `Button`, `NumberField` | нічого не знає про предметну область |
| `src/shared/storage/port.ts` | інтерфейс сховища — **що** потрібно | не знає, хто виконує |
| `src/shared/storage/local.ts` | реалізація через `localStorage` — **як** зроблено | імпортує тільки `app/` |
| `src/shared/priority/` | резерв під спільну модель пріоритету | у MVP не будуємо |
| `src/app/` | точка входу, реєстрація карток, склеювання | єдине місце, що знає все |

## Куди класти новий код

| Завдання | Куди |
|---|---|
| Нова картка користувача (здоров'я, кар'єра…) | **новий запис даних**, не нова папка — `life-area-card` один назавжди (D-23) |
| Новий тип блоку-метрики (не лише кількість+ціль) | бібліотека типів усередині `life-area-card/domain/`, без переписування коду (D-23, п.2) |
| Новий спільний елемент інтерфейсу | `src/shared/ui/` |
| Виклик бекенда (синхронізація, чат, авторизація) | новий файл поруч із `local.ts`, що реалізує той самий `port.ts`, або окремий `shared/backend/`. Картки не чіпаються |
| Розрахунок, спільний для всіх карток | `src/shared/` — але спершу ADR, бо це зміна меж |

## Межі й відомі компроміси

- **Синхронізація тепер є (D-24)** — попередній запис «дані не синхронізуються між
  пристроями» застарів; актуально: `localStorage`-кеш ~2 МБ, бекенд-база без жорсткого ліміту.
- **Прогрес позначається вручну або через чат з агентом.** Готових інтеграцій конекторів
  (Goodreads, Google Fit тощо) ще немає — місце заплановане на рівні бекенда.
- **Правило залежностей не перевіряється автоматично.** TypeScript цього не вміє; тримається на
  тому, що воно записане в `CLAUDE.md`.
- **Спільна модель пріоритету не спроєктована.** Зарезервоване місце `src/shared/priority/`,
  дизайн — окрема майбутня фіча.

## Стан

Каркас. Робочого коду ще немає — усі файли в `src/` є заглушками з поясненням, що там житиме.
